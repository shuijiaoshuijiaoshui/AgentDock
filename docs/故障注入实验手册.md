## E1 · 杀编排进程，挂起任务能否恢复

**操作**：发"帮我处理一下那个东西"触发澄清 → 挂起（input-required）→ `taskkill` 8300 进程 → 重启 → 带原 task_id/context_id 回填"查询 SKU-A001 的商品详情"。

**实测输出**：

```
[杀进程前] state: TASK_STATE_INPUT_REQUIRED
[杀进程前] clarify: {'question': '您是想「product_search」还是「product_lookup」？',
                     'type': 'clarify', 'options': ['product_search', 'product_lookup']}
[杀进程前] task_id: 786cee2b-1cec-4b4e-b116-620274b3320c
[杀进程前] context_id: 8807d64a-f812-416f-92bf-9308dd458922
（kill PID=3224 → 8300 已死（连接拒绝）→ 重启 → 200）
[重启后回填] 回填后的 state: TASK_STATE_COMPLETED
[重启后回填] 回答: 来自 merchandising（时点 ...）：{"name": "无线鼠标 Pro", "sku": "SKU-A001", ...}
```

**断掉的几种情况**：
1. ✅实测：挂起中进程被杀 → 重启后同 task_id 续跑成功（checkpointer 每步落库）。
2. 📖 代码路径：**彻底不重启** → 客户端超时报错，用户重发即新建 Task（旧挂起 Task 永远停在 input-required，无泄漏危害但占库）。
3. 📖 代码路径：**换端口重启**（Card 广播地址变）→ 旧 Card 缓存的调用方仍打旧端口 → 连接拒绝——这就是 Card URL 回连坑的变体。

**怎么修**：情况 2/3 无需修代码——重启用同端口同配置即可；生产上编排层应无状态多副本 + Task 存储外置（Postgres 已支持，切 CHECKPOINTER=postgres）。

**一句话总结**：*"任务挂起是每一步落库的，不是内存态——我杀过进程验证，重启后同 task_id 能续跑。"*

## E2 · 停售后域，串行链上游失败

**操作**：`Stop-Process` 杀 8304 → 发"SKU-A002 的退款，SO-2002 退到哪了"（串行链 售后→履约→财务）。

**实测输出**：

```
state: 3
final_text: 【售后域暂不可用】；【履约已取消：上游 aftersale 失败（unreachable: AgentCardResolutionError）】；【结算财务已取消：上游 aftersale 失败（unreachable: AgentCardResolutionError）】
aftersale.data : {"error": "unreachable: AgentCardResolutionError"}
fulfillment.data: {"error": "cancelled_by_upstream", "reason": "上游 aftersale 失败（unreachable: AgentCardResolutionError）"}
finance.data   : {"error": "cancelled_by_upstream", "reason": "上游 aftersale 失败（unreachable: AgentCardResolutionError）"}
veto 留痕: [{"cancelled": ["fulfillment", "finance"], "event": "veto",
             "reason": "上游 aftersale 失败（unreachable: AgentCardResolutionError）", "stage": "advance"}]
```

**断掉的几种情况**（域不可达一共 4 种形态）：
1. ✅实测：**进程没起/被杀** → AgentCardResolutionError → error 占位 + 下游取消。
2. ✅实测（历史/桩域行为）：**进程活着但明确拒绝** → Task REJECTED → 同样进 error 占位，表述为"暂不可用"（工作台工具面板走的就是这条）。
3. 📖 代码路径（`orchestrator/graph.py` domain_call）：**委托超时** → httpx 异常 → 与情况 1 同一个 except 分支，同样是 unreachable 占位——不会挂死主图。
4. 📖 代码路径：**域内部异常** → 域 executor 捕获后回 failed（"域内执行失败"）→ rejected/failed 分支 → 局部交付。
5. 📖 代码路径：**域反问（input-required）** → 并行场景该域局部交付并标注"需补充信息"，不阻塞其余分支。

**怎么修**：域挂了先 `dev_all` 重启对应进程（本实验杀掉后我单起 `uvicorn domains.aftersale.server:app --port 8304` 即恢复）。编排层**不需要修**——设计上就是局部交付；M4+ 可加一级重试 + 二级降级（代码注释里预留了位置）。

**一句话总结**：*"单域挂掉主图不会死——上游失败时下游标记取消而不是带病执行，答案里明确说哪个域不可用、哪个被取消。"*

## E3 · 财务故障注入 → Saga 补偿

**操作**：请求 metadata 带 `chaos=finance_settle_fail`，发"取消订单 SO-2001 给我退款"。

**实测输出**：

```
state: 3
final_text: 来自 order（...）:{"prev_status": "signed", "order_no": "SO-2001", "reason": "用户申请退款",
             "status": "cancelled", "verified": true, "biz_key": "e3-ctx:SO-2001:cancel"}；
            【结算财务域暂不可用】（本次跨域变更已全部回滚，Saga 补偿成功，无残留状态。）
order.data  : {"prev_status": "signed", ..., "status": "cancelled", "verified": true, "biz_key": "e3-ctx:SO-2001:cancel"}
finance.data: {"hint": "模拟财务域故障（chaos 注入），正向步骤失败，等待编排层补偿", "error": "chaos_injected", ...}
saga 留痕: [{"biz_key": "e3-ctx:SO-2001:cancel", "skill": "order.restore", "ok": true, "stage": "saga_compensate"}]
实测 DB：SO-2001 状态 = signed          ← 恢复了
实测 DB：SO-2001 退款单数 = 0           ← 没有悬挂
```

**断掉的几种情况**：
1. ✅实测：尾跳失败（chaos/真实故障）→ 补偿成功 → 无残留。
2. 📖 代码路径：**补偿执行失败**（如订单域也挂了）→ `saga_result=escalated`，委托人工坐席队列（handoff.accept），答案提示"已升级人工"。
3. 📖 代码路径：**连人工队列都不可达** → `escalation_failed` + logger.error——禁止静默是硬规则。
4. ✅实测（E8/E11）：**"补偿成功"的假象** → 任务 completed 但业务没生效 → 已修：成功判定看业务回执 `verified` 字段。

**怎么修**：真实故障先看 `finance.data.error` 定位（chaos_injected 是演练、no_bill 是业务、unreachable 是网络）；补偿失败按 decision_log 的 saga_compensate 条目追查 biz_key。

**一句话总结**：*"Saga 最坑的不是补偿逻辑本身，是'任务成功但业务没生效'的假象——我用 chaos 注入抓到过，修成校验业务回执。"*

## E4 / E5 · 审计哈希链：改与删

**操作**：经工作台 API 写 3 条审计 → sqlite 直改最后一条（E4）→ 删中间一条（E5）→ 每次 `GET /api/audit/verify`。

**实测输出**：

```
[写 3 条后] verify: {'ok': True, 'total': 3, 'broken_at': None, 'reason': None}
[改最后一条后] verify: {"ok": false, "total": 3, "broken_at": 55,
                         "reason": "第 55 条内容与哈希不符（被篡改）"}
[删 id=54 后] verify: {"ok": false, "total": 2, "broken_at": 55,
                       "reason": "第 55 条 prev_hash 断链（前一条被删除或篡改）"}
[重置后] verify: {'ok': True, 'total': 0, 'broken_at': None, 'reason': '审计日志为空'}
```

**断掉的几种情况**：
1. ✅实测：**改内容** → 重算哈希对不上存储值 → "内容与哈希不符"。
2. ✅实测：**删记录** → 后一条 prev_hash 指向不存在的哈希 → "prev_hash 断链"。
3. 📖 代码路径（`console/db.py` verify_audit_chain）：**绕过接口插入无哈希行** → "第 X 条缺少哈希（旧格式或链被绕过）"。
4. 📖 代码路径：**整链重写**（连 hash 一起重算）→ 本地校验发现不了；对策是把链尾哈希定期锚定外部存储（README M4 剩余项，诚实边界）。

**怎么修**：哈希链的"修"不是恢复数据，是**定位与追责**——broken_at 给出第一条被动记录，从这里查操作者。库文件被攻破属于安全事件，恢复靠备份。

**一句话总结**：*"我实测过：UPDATE 一条、DELETE 一条，校验接口都能精确报出第几条、什么原因——审计日志本身可篡改，追责就是空话。"*

**一句话总结**：*"我把路由改错一格，测试 0.7 秒就红——确定性路由的可测性就是买这个的。"*

## E7 · 把权限关掉

**操作**：`ensure_scope` 函数首行临时注入 `return True` → 跑三个工具合同测试文件 → 还原。

**实测输出**：

```
FAILED tests/test_tools_contract.py::test_scope_mismatch_rejected - KeyError: 'error'
FAILED tests/test_order_fulfillment.py::test_order_scope_rejected - KeyError: 'error'
FAILED tests/test_order_fulfillment.py::test_fulfill_scope_rejected - KeyError: 'error'
FAILED tests/test_finance.py::test_billing_scope_rejected - KeyError: 'error'
4 failed, 26 passed in 0.62s
（还原后 → 7 passed）
```

注意失败的形状：`KeyError: 'error'`——**权限被关掉后，越权调用拿到的是真实业务数据**，断言里找 `error` 字段当然找不到。这比"测试红"本身可怕得多：它演示了权限失效的实际后果是数据越权泄露。

**断掉的几种情况**：scope 失效三种形态——①默认放行（本实验，缺失 scope 的调用全放）✅；②写覆盖读判断写反 → 读接口拿 write 全过、写接口裸奔 📖；③scope 从请求体取而非 token claim → 伪造 scope 即越权（toB 文档重点，未实现租户级时以内部 token 信任边界为前提）📖。

**怎么修**：还原一行 + 保持"默认拒绝 + write⊇read + 按 intent 推导"三原则；测试里越权用例是**常驻哨兵**，不是装饰。

**一句话总结**：*"我把权限关了跑测试，4 个越权用例立刻红，失败形状是 KeyError——意味着真实数据被越权拿到了。默认拒绝不是洁癖，是数据边界的最后一道闸。"*

## E9 · 停政策域，三域并行降级

**操作**：杀 8306 → 发"SKU-A001 坏了，保修内还是保修外"（售后∥政策∥商品并行）。

**实测输出**：

```
final_text: 来自 aftersale（...）：{"degraded": true,
             "clause": "条款暂不可查（政策服务不可用），仅按 12 个月估算",
             "conclusion": "保修内", "sku": "SKU-A001", "eligible": true}；
            【政策域暂不可用】；
            来自 merchandising（...）：{"name": "无线鼠标 Pro", ...}
aftersale.data.degraded: True
policy.data: {"error": "unreachable: AgentCardResolutionError"}
merchandising.data.sku: SKU-A001
```

与 E2（串行）对照着记：**并行模式下没有"取消下游"**——三个域互不依赖，挂一个只影响自己；售后域内部对政策域有二次依赖（查保修条款），政策挂了它**降级而不是拒绝**：明确标注 `degraded=true` + "仅按 12 个月估算"，结论照给但依据打折。这就是"部分交付"两档：能答的答、不能答的明说、依赖缺失的降级标注。

**怎么修**：重启政策域即可；售后的 degraded 路径无需修（设计行为）。

**一句话总结**：*"并行链单域挂掉只影响自己那路；而售后对政策是内部依赖，我做了降级——结论照给但明确标注'条款不可查，按 12 个月估算'，绝不编一条条款出来。"*

## E10 · 碰壁两次自动转人工（含真实细节修正）

**操作**：经 console 渠道连发 5 条无法理解的输入。

**实测输出**（节选）：

```
[第1次] reply: 您是想「product_search」还是「product_lookup」？    ← 澄清，wall=0
[第2次] reply: 这个需求超出了我目前能处理的范围。...              ← nomatch，wall=1
[第3次] reply: 您是想「product_search」还是「product_lookup」？    ← 又澄清（新任务），wall=1
[第4条-新任务] reply: 已为您转接人工客服，坐席正在接入，请稍候。   ← wall=2 触发
[交接包] reasons: ['反复碰壁（2 次）'] | customer_id: CU-1003 | 历史: 1 条
[会话] status=pending_handoff
```

**实测修正了一个想当然的认知**：碰壁计数**只在 nomatch 时 +1，澄清不计**（`orchestrator/graph.py` understand 节点注释里写了"避免同一轮双计"）。所以"碰壁满 2"的真实路径是两轮"澄清→回填仍不懂→nomatch"，不是两次输入。交接包带上了客户身份和留档历史。

**断掉的几种情况**：①碰壁不累计（渠道层没回传 wall_count）→ 永远不自动转人工——console 的续传是靠 conversations.wall_count 列 📖；②高风险词路径（投诉/纠纷）不走碰壁，**直接**转人工（risk_flag 优先）✅ 实测于转人工闭环；③用户明确说"转人工" → 立即触发，与碰壁无关 ✅ 实测。

**怎么修**：若发现不自动转人工，按顺序查——conversation.wall_count 是否被渠道层更新 → artifact 里 hit_wall_count 是否 ≥2 → after_nomatch 条件。

**一句话总结**：*"碰壁计数是渠道层跨 Task 续传的，我实测过完整路径：澄清不计碰壁，nomatch 才计，满 2 交接包 reasons 就是'反复碰壁（2 次）'。"*

## E11 · 彩蛋真 bug：跨会话重复退款（实测发现 → 已修复）

**操作**：两个**不同 contextId** 的会话先后对同一订单 SO-2001 发起"取消订单并退款"。

**修复前实测输出**：

```
会话A finance.idempotent: False | refund_id: 2.0
会话B finance.idempotent: False | refund_id: 3.0     ← 第二笔退款！
实测 DB：SO-2001 的退款单 = [(2, 'SO-2001', 199.0, 'settled'), (3, 'SO-2001', 199.0, 'settled')]
```

**根因**：幂等键 `biz_key = contextId:订单号:refund` 只防"**同会话**重复"，两个会话的 biz_key 不同，`INSERT OR IGNORE` 拦不住——**同一订单被退了两次钱**。

**修复**（本次提交）：
1. `seed_mock.py`：业务级部分唯一索引——`CREATE UNIQUE INDEX idx_refunds_order_settled ON refunds(order_no) WHERE status='settled'`（发票同理 `idx_invoices_order_issued`）。一笔订单至多一张 settled 退款单，跨会话也成立。
2. `domains/finance/tools.py`：插入被索引拦下时（rowcount=0），**回查该订单已存在的 settled 退款单**返回，而不是按 biz_key 查空导致崩溃。

**修复后实测输出**：

```
会话A finance.idempotent: False | refund_id: 2.0
会话B finance.idempotent: True | refund_id: 2.0      ← 同一张单，幂等
最终实测：SO-2001 退款单 = [(2, 'settled')]
全量回归：107 passed
```

**排障插曲（真实）**：修复代码后第一次验证，会话 B 返回 None——原因不是修复无效，而是**运行中的财务服务还是旧代码**（改代码必须重启对应服务）。重启 8305 后立竿见影。这本身就是一条排障经验：Python 服务改代码不重启等于没改。

**一句话总结**：*"幂等测试我同会话测通了本以为完事，后来主动换了个会话打同一订单，真退出了两笔钱——修复是加业务级部分唯一索引，让'一单一退款'由数据库保证而不是由调用方自觉。这个案例我 总拿来讲：幂等键的粒度必须等于业务的去重维度。"*

## E12 · 系统代理劫持内部调用（换机/CI 必踩，实测）

**背景**：项目复制到新目录（`D:\work\AgentDock\code`）后，全新 `uv sync` + `uv run pytest`——**82 passed / 25 errors**，所有 e2e 在 fixture 阶段失败："orchestrator :xxxxx 未就绪"。

**排查过程（真实）**：
1. 手工同参数拉起服务 → uvicorn 正常监听，netstat 确认 `LISTENING`；
2. 但 pytest 的探活 `httpx.get("http://127.0.0.1:...")` 一直 ConnectError；
3. 对比测试：`trust_env=False` 直连 → **200**；
4. `urllib.request.getproxies()` → `{"http": "http://127.0.0.1:7897", ...}`——**Windows 系统代理（Clash 类工具）开着**。

**根因**：httpx 默认 `trust_env=True`，会读取系统代理（Windows 注册表 Internet Settings）。开启代理后，发往 `127.0.0.1:8300` 的**内部服务调用被劫持给代理** `127.0.0.1:7897`，代理不转发回环地址 → 全部 ConnectError → 多 Agent 协作整体瘫痪。同一份代码昨晚（代理未开）107 全过、今早（代理开启）25 个 e2e 全挂——**环境差异，不是代码回归**。

**实测输出**：

```
系统代理（httpx trust_env 读的就是这个）: {"http": "http://127.0.0.1:7897", "https": "...", "ftp": "..."}
[探活默认] card 请求失败: ConnectError [WinError 10061] 由于目标计算机积极拒绝
[trust_env=False] trust_env=False 直连: 200
[修复后全量] 107 passed in 43.86s     ← 系统代理保持开启状态下通过
```

**修复**：所有**内网调用**的 httpx 客户端显式 `trust_env=False`——共 8 处：`shared/a2a_client.py`（A2A 委托核心）、`shared/policy_client/client.py`、`scripts/dev_all.py`（就绪探测）、`scripts/smoke.py`、4 个 e2e 测试的探活与 fixture 客户端。

**断掉的几种情况**：
1. ✅实测：**本机代理开启** → 内网调用全部 ConnectError（本实验）。
2. 📖 企业环境：**强制代理 + SSL 中间人** → 即使 HTTPS 也会证书校验失败——`trust_env=False` 同样解决。
3. 📖 CI 环境：代理变量被 runner 注入 → 表现相同；也可用 `NO_PROXY=127.0.0.1,localhost`，但显式 `trust_env=False` 更可靠（不依赖环境配置）。

**怎么修**：内网客户端一律 `trust_env=False`；对外部 API（如智谱）则**保留** trust_env（企业网关可能需要代理）。

**一句话总结**：*"服务间调用永远走内网地址，必须绕过系统代理——我在换机部署时踩过：代理一开，所有 127.0.0.1 的 Agent 委托全部被劫持，25 个端到端测试全挂，一行 trust_env=False 解决。这类问题比拼的是排障路径：先证明进程在监听，再怀疑客户端链路。"*

## 给学习者的使用建议

1. **先读后跑**：每个实验的"操作"都是可直接复制的最小命令集；复跑任意一个的成本 ≤5 分钟。
2. **对照实验**：实验 1-10 与本手册 E1-E10 一一对应——本手册就是它们的参考答案。
3. **E11 单独记**：它是唯一一个"实测发现→定位→修复→回归"全流程的真 bug，讲排障能力时优先讲它。
4. **诚实边界**：表中标 📖 的路径是从代码推演的（分支逻辑确定，但本手册未制造该场景）——被追问时说"这个分支我没专门注入过，但代码路径是 XXX，我可以现场走一遍"。
