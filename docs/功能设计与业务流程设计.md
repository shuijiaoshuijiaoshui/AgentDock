# AgentDock · 功能设计与业务流程设计

> 项目：企业级 A2A 商家经营智能体中台（一主多子 + 人工坐席）
> 技术栈：LangGraph（编排）+ a2a-sdk 1.2.3（协议）+ 智谱 GLM（理解/合成）+ SQLite/Postgres（持久化）
> 配套：`PRD-AgentDock.md`（需求）、`docs/tour.html`（架构导览）、本文（功能设计与业务流程设计）

---

## 〇、痛点描述

### 痛点一：单 Agent 客服"答非所问"，且无法沉淀业务规则

***现状：***
*传统单 Agent 客服把"听懂、查数、算价、答疑、写单"全塞进一个提示词。商家经营场景里，成交价归订单管、库存归仓管、政策归法务管——单 Agent 只能靠模型"猜"，猜错没有兜底。*

***为什么痛：***

- *同一个问题两次问，答案可能不一样（模型自由编排，不可测）；*
- *跨域数据（价格 vs 库存）冲突时没有仲裁依据，容易"编一个看起来对的"；*
- *业务规则改动要改提示词，回归测试无从做起。*

***智能体解决方式：***
*做「一主多子」编排中台：主 Agent 只做"听懂 + 调度 + 合成"，业务查询拆成域 Agent（商品/售后/政策…），各自带工具查权威数据；路由由代码查表决定，不由模型决定。*

***价值：*** *同一句话 100 次同一条链路（可测、可审计、可定价），业务规则改动 = 加一行路由配置。*

### 痛点二：AI 接不住的问题，直接"死"给客户看

***现状：***
*模型置信度低的模糊输入、超出能力范围的请求、服务故障——单 Agent 系统对这些只有一种结局：硬答（编造）或报错。*

***为什么痛：***

- *编造比拒答更伤信任（"退款 7-15 天"被当成承诺）；*
- *没有人工兜底，客户流失在"和机器吵架"上；*
- *坐席接手时拿不到上下文，客户要把问题重说一遍。*

***智能体解决方式：***
*三级承接：低置信 → 澄清反问（interrupt 挂起，等客户回填）；连续碰壁/高风险/明确要求 → **转人工**，带结构化交接包（用户 id、域链结论、AI 草案、最近对话）；坐席工作台**双向聊天 + 全量查询工具 + AI 助手**辅助接单。*

***价值：*** *AI 接得住的自动化，接不住的优雅交给"知道用户是谁"的人——且交接零重复劳动。*

### 痛点三：业务数据散在各部门系统，口径打架

***现状：***
*商品价格在商品系统、成交价在订单系统、退款金额在财务系统。客服引用任何一个都可能和另一个冲突。*

***为什么痛：***

- *客服说"能退"，财务说"已超期"——互相矛盾；*
- *政策文本各系统存副本，过期版本被当成现行规定引用。*

***智能体解决方式：***
*权威源矩阵（每类事实只有一个域说了算）+ 政策域双形态（A2A 对外服务 + 内部只读 API 供各域引用，生效期硬过滤，过期版本绝不返回）。*

***价值：*** *跨域冲突有唯一解，答案可标注"数据来源 + 时点"，审计能定位责任。*



# 方案设计

## 一、需求分析

### 1.1 拆解痛点（痛点拆成 6 个具体问题）

| #    | 痛点的**具体表现**           | 谁受影响 | 现有系统能不能解决             |
| :--- | :--------------------------- | :------- | :----------------------------- |
| P1   | 同一问题两次问答案不同       | 商家     | ❌ 单 Agent 靠模型自由编排      |
| P2   | 查询结果没有权威口径         | 商家     | ❌ 各域数据散落，无人仲裁       |
| P3   | 模糊输入被硬答（编造）       | 商家     | ❌ 无澄清机制                   |
| P4   | AI 接不住就流失客户          | 商家     | ❌ 无人工兜底与上下文交接       |
| P5   | 坐席接单后两眼一抹黑         | 坐席     | ❌ 看不到客户是谁、AI 试过什么  |
| P6   | 服务故障整体不可用           | 全部     | ❌ 单点故障，无局部交付         |

**关键洞察**：这 6 个问题是一条因果链：

```
路由不确定(P1) ──► 口径打架(P2) ──► 模糊输入硬答(P3)
                                        │
                                        ▼
                            接不住就流失(P4) ──► 坐席无上下文(P5)
                                        │
                                        ▼
                            故障全挂，无局部交付(P6)
```

**所以设计的核心不是"加 6 个功能"，而是"打断这条因果链"**：

- 打断 P1：**路由查表（纯代码）**，LLM 只做理解与合成——同一句话 100 次同一条链
- 打断 P2：**权威源矩阵**写进域设计，跨域冲突留裁决器接口（M3）
- 打断 P3：**澄清 interrupt**，低置信反问而不是硬答
- 打断 P4：**转人工**（三触发：明确要求 / 碰壁≥2 / 高风险），交接包带全上下文
- 打断 P5：**坐席工作台**（客户身份显示 + 交接包 + 工具面板 + AI 助手）
- 打断 P6：**advance 并行调度 + 局部交付**——一个域挂了，其他域照答并标注

## 二、功能设计

### 2.1 六大能力

#### 能力①：确定性路由（advance 调度器）

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | 把"意图→哪些域、什么顺序"从模型手里拿走，变成**配置表 + 代码调度器** |
| **给谁用**   | 编排层内部（understand 之后、域委托之前）                     |
| **输入**     | 🟢 understand 产出的 `{intent, slots, confidence}`             |
| **输出**     | 一份 `Plan{domains[], mode}`，随后 advance 用 Send 把无入边域**并发扇出** |
| **更新时机** | 每轮对话即时查表                                              |
| **边界**     | ❌ LLM 不参与路由 ❌ 同一意图不因措辞变化走不同域链 ❌ 串行依赖边（M3）暂不支持 |

**为什么是"查表"而不是"模型决定下一步调谁"**：

- 教程里的 supervisor 模式让 LLM 每步决定下一个 Agent——同一句话两次请求可能走两条链
- 本项目的验收标准是"同输入 100 次同一条域链"（AC-21），只有查表能做到
- 新域接入 = 路由表加一行（AC-28），改配置不改代码

**为什么是"advance 循环"而不是"静态连边"**：

- 域数量是动态的（Plan 由查表得出），静态连边画不出来
- advance 每轮把"无未满足入边"的域用 `Send` 并发发出，收齐再发下一层——天然支持 M2 并行、M3 串行（同一段代码，不用重写）
- 每个域一个 `domain_call` 实例，输出经 reducer 并回主图，**并行安全是 reducer 保证的，不是靠锁**

#### 能力②：域 Agent 与统一 Artifact

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | 每个业务域一个独立 A2A Server（LangGraph 图 + 工具），产出**统一结构的 Artifact** |
| **给谁用**   | 编排层（消费 Artifact）、坐席工具面板（直调）                 |
| **输入**     | 🟢 编排委托文本（自然语言 + slots/trace_id 走 metadata；tenant/actor/scope 走 JWT claim） |
| **输出**     | `Artifact{authority_domain, skill, as_of, snapshot_id, data}` + 人话摘要 |
| **更新时机** | 每次委托即时执行                                              |
| **边界**     | ❌ 域内禁止横向委托（想跨域只能返回结论让编排重路由）❌ 不缓存业务数据副本 |

**为什么是"一域一进程"而不是"一 skill 一进程"或"全塞一个"**：

| 方案             | 问题                                                         |
| :--------------- | :----------------------------------------------------------- |
| 一 skill 一进程  | 部署单元爆炸（18 个），Card 发现、trace、评测成本 ×18        |
| 全塞一个 Agent   | 回到 P1：没有故障域隔离，财务挂了商品也不能答                |
| **一域一进程**   | 按数据边界切（订单/履约/售后各有独占数据），故障口径各自独立 |

**为什么 Artifact 强制带 `authority_domain / as_of / snapshot_id`**：

- `authority_domain`：这个数谁说了算（成交价=订单、到账时间=财务），跨域冲突时裁决器只认它
- `as_of`：数据的时点。"有货"不带时点等于没说
- `snapshot_id`：本次会话快照号，审计可回放"当时看到的是什么"

**为什么政策域是"双形态"（A2A + 内部只读 API）**：

- 政策条款既是独立问题（客户问"退货政策"→ A2A 委托），又是其他域推理的**原料**（售后判资格要引用条款）
- 原料引用走 `/internal/clauses` 只读 API（不建 Task）——把"查条款"做成任务会引入无意义的协议开销
- 权威文本只实现一份，各域永远拿到"生效版"（生效期硬过滤，过期版本绝不返回）

#### 能力③：澄清与碰壁承接

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | 低置信输入不硬答：反问一次（带 top-2 可点选项）；仍不确定则计入碰壁，两次碰壁自动转人工 |
| **给谁用**   | 客户（被反问时看到选项）、坐席（碰壁转来的工单）             |
| **输入**     | 🟢 understand 的 confidence、intake 的高风险词检测、渠道层续传的碰壁计数 |
| **输出**     | `input-required` Task（澄清挂起）或 handoff（转人工）        |
| **更新时机** | understand 节点内即时                                        |
| **边界**     | ❌ 澄清最多一次（禁止连环追问）❌ 高风险话术（投诉/纠纷）不反问，直接转人工 ❌ 澄清计数不跨会话 |

**为什么澄清挂起用 interrupt 而不是"把对话存表"**：

- LangGraph 的 `interrupt()` 天然把图停在某节点，**checkpointer 落库**；客户回填后 `Command(resume)` 从断点续跑
- 免费获得三件事：状态可恢复（进程重启不丢）、可审计（thread 历史完整）、多轮天然带状态
- 自己存表再"重放对话"等于手写一个 checkpointer，还要处理并发和幂等

**为什么碰壁计数存在渠道层（console）而不是图里**：

- 每轮对话是**新 Task**，图状态会重置——跨 Task 的计数只能放在活得更久的那一层
- console 每轮把计数塞进 metadata 带给编排，编排 +1 后经 Artifact 带回落库：**渠道层持会话态，编排层持任务态**，边界清晰

#### 能力④：人机协同（转人工 + 坐席工作台 + AI 助手）

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | AI 接不住时，把"结构化交接包"经 A2A 协议交给人工坐席工作台；坐席在双向聊天里接管，配套工具面板与 AI 助手 |
| **给谁用**   | 坐席（工作台全部）、客户（无感知——只是"换了个人服务"）       |
| **输入**     | 🟢 三触发：明确要求转人工 / 碰壁≥2 / 高风险词；客户身份（customer_id） |
| **输出**     | 交接包（9 字段）→ 坐席待接管队列 → 接管后双向聊天            |
| **更新时机** | 触发即转；坐席回复经 WebSocket 实时到客户页                  |
| **边界**     | ❌ 澄清挂起中的会话不可接管（409）❌ 交接包不含完整聊天记录（坐席按 contextId 自己拉）❌ 写类工具（退款结算）不上工作台（M4） |

**交接包九字段**（每个都有"坐席为什么要"的答案）：

| 字段             | 坐席用它干什么                                               |
| :--------------- | :----------------------------------------------------------- |
| `context_id`     | 拉完整对话历史（转人工=新 Task、contextId 不变）             |
| `customer_id`    | 知道客户是谁 → 工具面板直接查他的信息（行级权限依据）        |
| `trace_id`       | 定位这次 AI 是怎么走的（哪条域链、哪步出问题）               |
| `reasons`        | 为什么转过来（要求/碰壁/高风险）——决定接待语气              |
| `domain_artifacts` | AI 动过哪些域、拿到什么结论——不用重新查一遍               |
| `decision_log`   | AI 的决策痕迹（澄清问过什么、哪里 nomatch）                  |
| `ai_draft`       | AI 草案，一键采用或修改（80% 的场景直接用）                  |
| `user_text`      | 客户最后这句话                                               |
| `history`        | 最近 6 轮原文（快速进入语境）                                |

**为什么坐席侧还要一个"AI 助手"（主 Agent 的 toB 入口）**：

- 坐席接单后经常遇到自己也不会的问题——重新去各系统查，效率低
- AI 助手 = 坐席直接问主 Agent（和客户用的是**同一张主图、同一条路由**），答案一键插入回复框
- toC 客户与 toB 坐席**双入口并存**：编排是无状态任务处理器，谁问都走同一条链——这是"一主多子"架构的天然红利，一行代码没改就支持了

**为什么实时通道是 WebSocket 而不是 SSE**：

- 人工对话是**双向持续**的：客户和坐席谁都能先开口，还有"接管/交还"状态变更
- SSE 只能服务端单向推，配上 REST 发就是两条通道两套状态
- WS 按会话维护连接注册表扇出——多实例部署时这一层换 Redis pub/sub（预留注释）

#### 能力⑤：并行调度与局部交付

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | 一次意图可并发委托多个域（如"机器坏了问保修"→ 售后∥政策∥商品），单域故障不影响其他域 |
| **给谁用**   | 编排层；客户只看到"一次提问、一条合成答案"                   |
| **输入**     | 🟢 Plan（含多个域）                                          |
| **输出**     | 各域 Artifact 经 reducer 合并；缺席域占位 `error`，合成时标注"XX 域暂不可用" |
| **更新时机** | 每轮即时                                                      |
| **边界**     | ❌ 串行依赖边（售后→履约→财务）不支持（M3）❌ 不做跨域重试（一级重试 M3 接） |

**为什么并行下"域追问"改为局部交付而不是挂起**：

- 单域链路：域追问 → ask_user interrupt → 回填续跑（体验最好）
- 并行链路：三个 Send 同时在飞，若某个域要求挂起，会产生"多分支同时写 pending_task"的冲突
- 取舍：并行下把该域标为"需补充信息"局部交付，其余域照常——**宁可少一块信息，不要一个卡死的会话**

#### 能力⑥：可观测与审计

| 项           | 内容                                                         |
| :----------- | :----------------------------------------------------------- |
| **是什么**   | 每轮生成 trace_id 全链透传；关键决策写 decision_log；工具调用全量审计 |
| **给谁用**   | 坐席（audit 查询）、开发（日志排障）、未来对账（M4）         |
| **输入**     | 🟢 每轮对话、每次工具调用                                     |
| **输出**     | trace_id 进 metadata/日志；`audit_log` 表（工具/参数/结果摘要）；`decision_log`（澄清/路由/委托/转人工） |
| **边界**     | ❌ 审计不落客户敏感明文（手机号入库即脱敏）❌ 哈希链与 OTel（M4） |

### 2.2 完整数据流

```
客户消息(带 customer_id)
   │ WS / REST
   ▼
console：落 messages ──► A2A 委托编排（新 Task，同 contextId，
   │                      metadata: trace_id/customer_id/wall_count/scope）
   ▼
编排主图
   intake(规范化+风险词+装载状态)
     → understand(LLM: intent+slots+confidence)
         ├─ 低置信 → interrupt 澄清（Task=input-required → console 记 pending）
         └─ 确认 → route(查表 → Plan)
     → advance(拓扑调度)
         ├─ Send ──► domain_call(商品) ──► 商品域 ReAct ──► Artifact
         ├─ Send ──► domain_call(售后) ──► 售后域 ReAct ──► Artifact
         └─ Send ──► domain_call(政策) ──► 政策域 ReAct ──► Artifact
     → synthesize(带来源与时点合成；缺席域标注)
     → deliver(校验) → Artifact{final_answer, handoff, wall_count}
   ▼
console：读回复 ──► 落 messages(role=ai) ──► wall_count/handoff 写回
   │
   ├─ 正常 ──► WS ──► 客户页
   └─ handoff=true ──► A2A 委托人工坐席（handoff.accept）
                          → handoff_queue 入队 → 坐席接管 → WS 双向聊天
```

### 2.3 关键设计决策的权衡

| #    | 决策点               | 选项 A          | 选项 B            | 选了谁 | 为什么                                                        |
| :--- | :------------------- | :-------------- | :---------------- | :----- | :------------------------------------------------------------ |
| D1   | 路由决策者           | LLM supervisor  | 路由表查表        | **B**  | 确定性可测（AC-21）；权限/成本不能赌在概率上                  |
| D2   | 域间协作             | 子图嵌套        | A2A 独立进程      | **B**  | 部署/评测/故障域隔离；协议化后未来可换团队维护                |
| D3   | 澄清实现             | 对话存表重放    | interrupt+resume  | **B**  | 免费获得可恢复/可审计；自建重放=手写 checkpointer             |
| D4   | 碰壁计数存储         | 图状态          | 渠道层续传        | **B**  | 每轮新 Task 图状态会重置；会话态归渠道层                      |
| D5   | 转人工交接           | 聊天记录全量    | 结构化 9 字段     | **B**  | 坐席要结论不要流水；历史按 contextId 可拉                     |
| D6   | 实时通道             | SSE             | WebSocket         | **B**  | 人工对话双向持续；单问一答才轮到 SSE                          |
| D7   | 并行下域追问         | 挂起整链        | 局部交付标注      | **B**  | 多分支写 pending 会冲突；宁缺一块信息不卡死会话               |
| D8   | 桩域被调用           | nomatch 挡住    | 放行→明确"暂未开放" | **B** | 权限面先行、数据后补；M3 点亮后同一路由自动变真数据           |
| D9   | 客户身份             | 坐席自己问      | 客户页声明+全程透传 | **B** | 交接包、行级权限、审计都挂在 customer_id 上                   |
| D10  | 政策引用方式         | 各域存条款副本  | 内部只读 API      | **B**  | 副本必然过期（R11）；生效期过滤只实现一份                     |



## 三、业务流程设计

### 3.1 角色与场景速览

#### 3.1.1 三个角色

| 角色       | 谁           | 在系统里的职责                         | 关心什么                     |
| :--------- | :----------- | :------------------------------------- | :--------------------------- |
| **客户**   | 商家经营者   | 提问、补澄清、等人工、评价答案         | "我的问题解决了吗""快不快"   |
| **坐席**   | 人工客服     | 接管会话、查工具、用 AI 助手、回复客户 | "客户是谁""AI 试过什么""怎么快速答" |
| **系统**   | 9 个服务     | 路由、扇出、合成、转接、留痕           | （无）                       |

#### 3.1.2 八类典型场景

| #    | 场景                     | 谁发起 | 何时             | 谁最终处理           |
| :--- | :----------------------- | :----- | :--------------- | :------------------- |
| S1   | 客户问商品（查/比/价）   | 客户   | 任意时刻         | 系统自动（单域）     |
| S2   | 客户问售后（资格/工单）  | 客户   | 任意时刻         | 系统自动（单域）     |
| S3   | 客户问"坏了+保修"        | 客户   | 任意时刻         | 系统自动（**三域并行**） |
| S4   | 客户模糊提问被澄清       | 客户   | 置信 < 0.6       | 系统挂起 + 客户回填  |
| S5   | 客户连续碰壁             | 系统   | 碰壁≥2           | 系统转人工           |
| S6   | 客户要求转人工/高风险    | 客户   | 任意时刻         | 系统转人工（立即）   |
| S7   | 坐席接管与人工服务       | 坐席   | 待接管出现时     | 坐席                 |
| S8   | 坐席交还 AI              | 坐席   | 人工解决完毕     | 系统自动（AI 接续）  |

**💡 本节的用途**：读者第一眼看到全貌——**客户看 S1-S4，坐席看 S5-S8**。后面 3.2/3.3 分别展开两条旅程。

### 3.2 客户旅程全景（核心图）

> **本节回答**：客户从"提问"到"解决"的全程，每一步看到什么、系统做什么、多久返回。

#### 3.2.1 客户旅程总览（五阶段）

```
阶段 1：提问        阶段 2：等待        阶段 3：补答        阶段 4：人工        阶段 5：收尾
─────────          ─────────          ─────────          ─────────          ─────────
"输入问题"          "AI 查数"           "回答澄清/          "和真人聊"          "问题解决
                                         等转接"                                交还 AI"

   │                  │                  │                  │                  │
   ▼                  ▼                  ▼                  ▼                  ▼
 页面即时回显        秒级拿到答案        点选项或打字        坐席已接入提示      AI 无缝续答
 (WS 本地回环)       带来源与时点        (interrupt 挂起)    (交接包已读)       (同 contextId)
```

#### 3.2.2 设计要点

| 阶段         | 客户做什么         | 客户看到什么               | 系统做什么                     | 返回时长   |
| :----------- | :----------------- | :------------------------- | :----------------------------- | :--------- |
| 阶段 1 提问  | 输入消息           | 消息即时上屏               | 落库、扇出、委托编排           | 即时       |
| 阶段 2 等待  | 等答案             | **带来源与时点的合成答案** | 主图全链（理解→路由→扇出→合成） | 秒级（fake 模式 <1s） |
| 阶段 3 补答  | 点选项/打字        | 澄清问题（top-2）          | interrupt 挂起 → resume 续跑   | 挂起不计费时长 |
| 阶段 4 人工  | 和坐席聊           | "人工客服已接入"           | 交接包已入队、坐席已读上下文   | 坐席响应时长 |
| 阶段 5 收尾  | 继续问别的         | AI 无缝接答                | 交还 AI，同 contextId 续       | 即时       |

**💡 客户体验的三个关键节点**：

1. **阶段 2 的来源标注**：答案里每个数都带"来自 XX 域（时点 …）"——客户能判断新旧，坐席能对账。这不是技术噪音，是信任设计。
2. **阶段 3 的一次性**：AI 只反问一次，且给可点选项（不用打字）。反问第二次等于告诉客户"机器没懂"——两次没懂就转人。
3. **阶段 4 的零重复**：坐席接手时客户**不需要重说一遍**——交接包已带身份、AI 试过的域链和草案。这是人机协同的底线。

### 3.3 坐席旅程全景

#### 3.3.1 坐席旅程总览（四阶段）

```
阶段 1：发现          阶段 2：研判           阶段 3：处置            阶段 4：收尾
─────────            ─────────              ─────────              ─────────
"列表弹出待接管"      "读交接包看上下文"      "聊天+工具+AI 助手"     "交还 AI 或关闭"

   │                    │                      │                       │
   ▼                    ▼                      ▼                       ▼
 徽标高亮(3s 刷新)     客户是谁/AI试过啥       查用户信息·查商品        系统消息确认
                      触发原因决定语气         一键插入回复框           会话回到 AI
```

#### 3.3.2 设计要点

| 阶段         | 坐席做什么         | 坐席看到什么               | 系统支撑                       |
| :----------- | :----------------- | :------------------------- | :----------------------------- |
| 阶段 1 发现  | 扫会话列表         | 橙色"待接管"徽标           | 3 秒轮询 + WS 双通道           |
| 阶段 2 研判  | 点开会话           | 交接包卡（9 字段）+ 历史   | contextId 拉全史               |
| 阶段 3 处置  | 回复/查数/问 AI    | 客户身份、工具面板、AI 助手 | A2A 直调域 + audit 留痕       |
| 阶段 4 收尾  | 点"交还 AI"        | 系统消息"已交回"           | mode=ai，同 contextId 续答     |

**💡 坐席效率的三个杠杆**：

1. **研判零成本**：交接包把"客户是谁、AI 试过什么、卡在哪"三件事前置——坐席上线即可说话，不用翻记录。
2. **处置双通道**：确定的问题用工具面板（单点直查，秒回）；拿不准的问 AI 助手（走全链路，带来源）。**AI 回答可一键插入回复框**——查到→采纳→发出，三步并一步。
3. **收尾不丢上下文**：交还 AI 后同一 contextId 继续——客户感知"还是同一个会话"，坐席的回复留在历史里供 AI 参照。

### 3.4 三类转人工触发对比

| 触发类型     | 谁发起 | 判定条件                     | 客户感受                 | 坐席看到                 |
| :----------- | :----- | :--------------------------- | :----------------------- | :----------------------- |
| **明确要求** | 客户   | intent=request_human         | 秒转，无反问             | reasons="用户明确要求"   |
| **碰壁自动** | 系统   | 碰壁计数 ≥ 2（澄清后仍不确定 / 拒答累计） | 第二次碰壁后自动转接 | reasons 含碰壁次数       |
| **高风险**   | 系统   | 投诉/纠纷/315 等话术命中     | **不反问**，直接转接     | reasons="高风险话术"     |

**💡 为什么高风险不先澄清**：投诉场景里多问一句"您是想 A 还是 B"等于火上浇油。三类触发的优先级都在路由条件边里（先于一切业务路由），判定是代码不是模型。

### 3.5 关键对象的状态流转

**A2A Task（每次委托一个）**：

```
SUBMITTED ──► WORKING ──► COMPLETED（Artifact 下发）
                 │
                 ├─► INPUT-REQUIRED（interrupt 挂起）──回填──► WORKING（resume 续跑）
                 ├─► REJECTED（权限/桩域明确拒绝，不重试）
                 └─► FAILED（域内异常）
```

**工作台会话 conversation（跨 Task 的会话壳）**：

```
active ──触发转人工──► pending_handoff ──坐席接管──► with_human ──交还──► active
                           │
                           └─（客户此时继续发言）──► 消息入流，坐席实时可见
```

**交接单 handoff_queue**：

```
pending（待接管）──接管──► taken ──交还 AI──► returned
```

**💡 三个状态机的关系**：Task 是"一次委托"的生命周期，conversation 是"一个客户会话"的生命周期，handoff_queue 是"一次交接"的生命周期。三者靠 **contextId（= 会话 id）** 对齐——这就是为什么"转人工 = 新 Task、contextId 不变"是全系统的锚点设计。

### 3.6 异常与降级路径

| 异常                     | 系统行为                                       | 客户看到                     | 出处           |
| :----------------------- | :--------------------------------------------- | :--------------------------- | :------------- |
| 意图不在路由表           | nomatch：拒答 + 列出全部开放能力 + 提示转人工  | 明确的能力清单               | route/nomatch  |
| 域服务不可达（进程死）   | 该域占位 error，**其余域照常**，合成标注"XX 域暂不可用" | 部分答案 + 降级说明          | domain_call 兜底 |
| 域返回 rejected（桩/权限） | 不重试，同样局部交付标注                      | "XX 域暂不可用（M3 交付）"   | domain_call    |
| 澄清后仍不确定           | 碰壁 +1；累计 2 次 → 当场转人工                | "已为您转接人工客服"         | after_nomatch  |
| 政策服务不可用（域内引用） | 售后判定降级为"按 12 个月估算"并标注 degraded  | 结论保留 + 依据标注"暂不可查" | PolicyClient   |
| 转人工本身失败           | 兜底话术 + 服务热线                            | 明确的替代路径               | handoff 节点   |
| 条款无生效版本           | "未找到生效条款"（绝不返回过期版）             | 诚实拒答                     | 生效期硬过滤   |

**💡 降级的设计原则**：每一级都要回答"客户此刻最少需要知道什么"。宁可说"这一块暂时查不了"，不编一个数；宁可局部交付，不整体报错。

### 3.7 业务流程 ↔ 代码节点映射

| 业务步骤（3.2/3.3） | 主图节点 / 模块                | 一句话职责                   |
| :------------------ | :----------------------------- | :--------------------------- |
| 理解客户说什么      | `understand`                   | LLM 结构化输出意图+槽位+置信 |
| 决定走哪条链        | `route` + `route_table`        | 纯代码查表（AC-21）          |
| 并发查多个域        | `advance` + `domain_call`      | Send 扇出 + 单域委托         |
| 域内多步推理        | 域图（ReAct）+ 工具            | 查权威数据，产 Artifact      |
| 反问澄清            | `interrupt` / `ask_user`       | input-required + 回填续跑    |
| 合成人话            | `synthesize` + `deliver`       | 带来源标注 + 局部交付标注    |
| 转人工              | `handoff` 节点 + HumanDeskExecutor | 交接包 → 队列 → 工作台   |
| 人工对话            | console WS + ConvSockets       | 按会话扇出                   |
| 留痕                | decision_log / audit_log       | 全程可回放                   |

### 3.8 并发场景与一致性

| 场景                     | 一致性手段                                                   |
| :----------------------- | :----------------------------------------------------------- |
| 三域并行写结果           | `artifacts` 用 merge_dict reducer（每分支只写自己的 key）；`decision_log` 用 merge_list（拼接） |
| 坐席与客户同时发消息     | 单写者原则：消息只经 `handle_customer_message/handle_agent_reply` 落库+扇出，REST/WS 共用同一函数 |
| WS 多端同会话            | 扇出注册表按会话分发，客户端按消息 id 去重追加               |
| 澄清回填与转人工竞争     | 澄清挂起中的会话不可接管（409）；状态机单向流转              |
| 多实例部署（未来）       | WS 扇出换 Redis pub/sub；console.db 换 Postgres（TaskStore 已有实现） |

**💡 一句话总结**：业务流程里的每一步"谁在什么时候看到什么"，背后都是"哪个节点在什么状态机上做了一次确定性迁移"——流程图和代码是一一对应的，这是本方案可维护性的根本。
