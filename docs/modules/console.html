注意点（设计取舍与已知边界）

🔴 WS 鉴权自管（中间件不覆盖 ws scope）

Starlette BaseHTTPMiddleware 只处理 http scope——WebSocket 请求不会过鉴权中间件。ws_chat 端点内自校验：连接后首包 {"type":"auth","token":JWT}（1C 起替换 query 参数），验签取 tenant/actor/role，并校验 Origin 白名单。
console/server.py:2159 ws_chat · shared/auth.py:223 auth_from_headers

🟡 扇出注册表是进程内的

ConvSockets 是 dict——单实例够用；多实例部署同会话连接会落在不同进程，届时此处换 Redis pub/sub（代码注释与 README 已标注，这是本项目 Redis 的正确出场时机）。
console/server.py:199（进程内 dict）· 说明见 README

✅ REST 与 WS 共用写库路径

handle_customer_message / handle_agent_reply 是唯一写入口：无论消息从 WS 还是 REST 进来，落库与扇出行为一致——避免双通道状态漂移。REST 保留作建会话与兜底。

✅ 渠道层持会话态（wall_count / history）

每轮对话是新 Task，图状态会重置——碰壁计数与多轮历史都活在更长寿的渠道层：wall_count 存 conversations、M4 摘要存 session_summaries，每轮经请求级 metadata 进图，产物回写。编排无状态可横向扩，会话态有唯一属主。
