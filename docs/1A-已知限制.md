# 1A / 1B 已知限制

记录 1A（数据与越权）、1B（审计/审批/确认）完成后仍未闭环的事项，避免把 demo 能力误当成生产能力。

## Postgres / 多实例

- `a2a_tasks` 已改为 `(tenant_id, task_id)` 复合主键；SQLite 旧表的自动迁移有测试覆盖。
- `PostgresTaskStore` 的迁移是 best-effort：启动时尝试 drop 旧主键并加复合主键，失败会保留原状（异常被吞掉）。尚未在真实 Postgres/compose 上验证；在 compose 环境首次升级前应重置 `a2a_tasks` 或人工确认主键。
- 业务库仍默认 SQLite（`infra/mockdata/mock.db`，可由 `BUSINESS_DB_PATH` 覆盖）；多进程写只适合本地 demo。生产必须在 Phase 2 前切换 Postgres。
- securityd 已提供审计/审批/确认单写者：本地单测 `SECURITY_MODE=local`，dev_all/compose 使用 `remote`；securityd 自身仍用 SQLite，生产多实例需换 Postgres/HA，并把 securityd 作为高可用单点治理。
- securityd 是 strict 审计路径的单点：securityd 不可达时，高价值动作会失败关闭（503/异常），这是预期安全行为；生产需健康检查、重试与告警。

## 业务规则

- 售后资格仍按硬编码 365 天判定；1A 只修了“购买日期来源”，政策条款驱动的保修期在 Phase 2 处理。
- `console/db.py` 内部仍有 `DEFAULT_TENANT = "t_demo"` 默认值；认证入口都显式传 tenant，但 Phase 2/4 应移除默认回落。
- `finance` 角色登录工作台后部分接口 403、UI 初始化中断，放在 Phase 4 修。
- `/` 路径被 JWT 中间件放行是登录页设计，不是跨客户越权。

## 审计 / 审批 / PII / 前端

- `console/db.py` 的 `audit_log` 已停止写入，仅保留历史表；工作台 `/api/audit*` 与统一审计链一致。若旧库仍有历史 `audit_log`，它不再参与校验。
- 审批单已改 UUID，pending/approved 都校验过期；consume 绑定申请人/动作/对象/金额，一单一次；只有申请人或 `finance/supervisor/admin` 可消费。
- 确认单为服务端一次性 token，绑定 tenant/actor/customer/action/target/payload hash；`pending_actions` 持久化在 console.db。
- PII 进入 LLM、工作台 XSS/CSP、Cookie/CSRF 待 1C。
- `order_price_amend` 是 1A 之前 WIP 中已有的功能；1A/1B 只对 `order.amend`/审批链做了对象级授权与确认，没有扩展该功能。
- securityd 的服务间认证使用短时 service JWT（aud=securityd）；用户 token 会被拒绝。生产仍需网络隔离、密钥轮换和审计告警。
