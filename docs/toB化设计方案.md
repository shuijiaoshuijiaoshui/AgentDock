## 〇、一句话结论

**当前项目是「单租户的 toC 客服 Demo」，toB 化要补的不是功能，是「隔离 + 归属 + 追责」三件事。**

| 维度 | toC Demo（现在） | toB SaaS（目标） | 差距性质 |
| :--- | :--- | :--- | :--- |
| 使用主体 | 一个商家 | N 个商家，互相不可见 | **数据隔离** |
| 用户角色 | 客户 + 坐席（无身份） | 商家管理员 / 客服主管 / 坐席 / 客户，四级 | **权限模型** |
| 数据归属 | 会话不属任何人 | 每条数据必须能回答"属于哪个租户、哪个人" | **归属链路** |
| 出问题时 | 看不到谁干的 | 能追到"谁、在哪个租户、什么时候、做了什么" | **审计追责** |
| 交付形态 | 本地 dev_all 起服务 | 租户可开通、可限额、可计费 | **商业化** |

## 一、toB 化的五个硬门槛（按不可妥协程度排序）

### 门槛 1：多租户隔离（PRD FR-5.1，代码 0 实现）

**现状证据**
```
$ grep -rn "tenant" --include="*.py" .
（无输出）
```
- `PRD-AgentDock.md:486`："系统槽位 `tenant_id`…**禁止从自然语言获取，禁止信任请求体**"
- `PRD-AgentDock.md:595`：FR-5.1「租户间数据与知识完全隔离」
- 代码：`console/db.py` 的 `conversations` 表只有 `customer_id`，**没有 tenant_id**；`mock.db` 的 `products/customers/policy_docs` 全库共享

**为什么这是硬门槛**
1. 两个商家同时用，A 商家的坐席能看到 B 商家的会话 → **一票否决级事故**
2. 政策条款、商品数据不隔离 → 定价/规则互相污染
3. 没有 tenant_id，后续计费、配额、SLA 全部无从谈起

**toB 要求**
- 每个请求必须携带 `tenant_id`，且**只从 token claim 取，不从请求体取**
- 所有表加 `tenant_id`，所有查询强制带租户过滤（行级）
- 跨租户访问一律 404（不是 403，避免探测租户是否存在）
- Mock 数据按租户分片（或加租户前缀）

### 门槛 2：坐席身份与归属（现在完全没有）

**现状证据**
```
console/server.py:336  if role == "agent":     ← role 只是 WS query 参数
console/db.py:41       role TEXT ... role=customer|ai|agent|system
```
- **没有坐席表**，没有 `agent_id`，没有 `operator_id`
- 审计表 `audit_log(conversation_id, tool_id, params, result_summary, created_at)` —— **不知道是谁调的**
- 接管动作 `take_handoff` 只改状态，**不记录"谁接管了"**
- WS 连接 `?as=agent` 任何人都能声明自己是坐席

**为什么这是硬门槛**
1. "谁把我的客户接走了""谁给这个客户建了工单"——**答不出来，SaaS 无法交付**
2. 坐席绩效（接单量/首响/解决率）无从统计
3. 越权取证时无法定位责任人

**toB 要求**
- 坐席表：`agents(agent_id, tenant_id, name, role, skill_groups[], status)`
- 会话归属：`conversations.assigned_agent_id`、`handoff_queue.taken_by`
- 审计四要素：`tenant_id + actor_id + action + target`
- WS 鉴权：`?as=agent` 换成真实坐席 token（现在只是字符串声明）

### 门槛 3：角色与权限模型（不只 scope，还要 RBAC）

**现状证据**
- 只有两级：内部 token（全权限）/ 无 token（拒绝）；其中 `ensure_scope` 只区分 `domain.read/write`
- **没有角色概念**：商家管理员、客服主管、坐席，权限完全一样

**toB 要求的三层权限**
```
L1 租户级：tenant × 域（A 商家不能查 B 商家的订单）
L2 角色级：RBAC —— 管理员(全部) / 主管(看板+接管+导出) / 坐席(只管自己的会话)
L3 行级：   坐席只能看 assigned_agent_id = 自己的会话；客户只能看自己的 customer_id
```
**关键设计**：L2/L3 必须是**服务端强制**的，前端隐藏按钮不算权限。

### 门槛 4：审计与合规（toB 采购的必查项）

**现状证据**
- `audit_log` 缺 `tenant_id / actor_id / ip / user_agent`
- 无导出（商家要"给我这三个月的客服记录"）
- 无留存策略（SaaS 通常要求 6 个月～3 年）
- 无数据删除接口（GDPR/个保法的"被遗忘权"）

**toB 要求**
- 审计表补齐四要素 + 只追加（append-only）
- 按租户导出（CSV/JSON，异步任务 + 下载链接）
- 留存与归档策略（热 90 天 / 冷 3 年）
- 数据删除工单（客户注销 → 级联删 + 留删除审计）

### 门槛 5：运营与商业化能力

**现状证据**：无配额、无计量、无计费、无租户级看板

**toB 要求**
- 用量计量：会话数、Token 消耗、工具调用次数、坐席数
- 配额与限流：按套餐限月会话数 / 并发坐席数
- 租户级看板：转人工率、首响时长、解决率、AI 拦截率
- 计费：按席位 or 按用量（通常 "席位 + 超额用量"）

## 二、目标架构：租户贯穿全链路

### 2.1 数据模型改造

```
┌──────────────────────────────────────────────────────────────┐
│ tenants（租户）                                                │
│  tenant_id · name · plan · status · created_at                │
└───────────────┬──────────────────────────────────────────────┘
                │ 1:N
    ┌───────────┼────────────┬──────────────┬─────────────┐
    ▼           ▼            ▼              ▼             ▼
 agents      customers   conversations   policy_docs   audit_log
 (坐席)      (客户)       (会话)          (政策/按租户)  (审计)
 ·tenant_id  ·tenant_id  ·tenant_id      ·tenant_id    ·tenant_id
 ·name       ·name       ·customer_id    ·clause_id    ·actor_id
 ·role       ·phone      ·assigned_      ·version      ·action
 ·skills[]   ·tier         agent_id      ·tenant_id    ·target
                         ·status                       ·ip
```

**改造清单（按表）**

| 表 | 新增字段 | 说明 |
| :--- | :--- | :--- |
| 新增 `tenants` | — | 租户主表 |
| 新增 `agents` | tenant_id, role, skill_groups | 坐席（含主管/管理员角色） |
| `conversations` | **tenant_id**, assigned_agent_id | 租户+坐席归属 |
| `messages` | tenant_id（冗余，便于分区） | — |
| `handoff_queue` | tenant_id, taken_by（agent_id） | 谁接的单 |
| `audit_log` | **tenant_id, actor_id, actor_role, ip, user_agent** | 追责四要素 |
| `assist_messages` | tenant_id, agent_id | 坐席 AI 助手也归租户 |
| `products/customers/policy_docs` | **tenant_id**（联合主键） | 业务数据隔离；政策可按租户定制 |

**索引**：所有表的 `(tenant_id, ...)` 组合索引放第一位——**保证行级过滤走索引，不是全表扫**。

### 2.2 身份与鉴权链路

```
① 登录（企业 SSO / 账密）
   用户 → 认证服务 → JWT{ tenant_id, actor_id, role, scopes[] }
                                    │
② 每个请求带 JWT（HTTP Header / WS 首包）
                                    │
③ 网关/中间件：验签 → 提取 tenant_id/actor_id/role → 注入 RequestContext
                                    │
④ 业务层：所有 SQL 强制 tenant_id 过滤；RBAC 检查；行级 owner 检查
                                    │
⑤ 审计：每个写动作记 { tenant_id, actor_id, action, target, before/after }
```

**关键约束**（PRD 486 行原文）：`tenant_id / customer_id / scope` **禁止从自然语言获取，禁止信任请求体**——只从 token claim 取。

**现状与目标的映射**

| 环节 | 现在 | 目标 |
| :--- | :--- | :--- |
| 鉴权 | 单一 `INTERNAL_TOKEN` | 每用户 JWT（tenant/actor/role/scopes） |
| scope 来源 | metadata 里调用方自称 | token claim（不可伪造） |
| WS 身份 | `?as=agent` 字符串 | WS 首包 JWT 认证 |
| 客户身份 | `customer_id` 请求体传入（**可伪造**） | 登录态绑定，token claim |

### 2.3 请求上下文贯穿

```
客户请求 → console（注入 tenant_id/actor_id）
         → A2A metadata（tenant_id/actor_id/trace_id）
         → 编排 intake（读入 state，进系统槽位）
         → domain_call（metadata 透传）
         → 域工具（SQL 强制 tenant 过滤）
         → Artifact（携 tenant_id，便于审计回溯）
```

**落点建议**：`OrchestratorState` 增加系统槽位（不进自然语言）：
```python
tenant_id: str      # 系统槽位，从 token claim 注入
actor_id: str
actor_role: str     # admin / supervisor / agent
```

## 四、实现路线（三阶段，每阶段可独立交付）

### 阶段一：隔离与身份（P0，约 2-3 天）

**目标**：两个租户同时用，数据互不可见；谁做的操作查得到。

1. **建表**：`tenants`、`agents`；所有业务表加 `tenant_id`（迁移脚本 + 现有数据补默认租户）
2. **身份**：`console/db.py` 加租户/坐席查询；WS 首包认证（替换 `?as=agent`）
3. **鉴权**：`shared/auth.py` 的中间件改为「解析 JWT → 注入 tenant_id/actor_id」，`INTERNAL_TOKEN` 只保留服务间调用
4. **行级过滤**：所有 SQL 加 `WHERE tenant_id = ?`；`conversations` 加 `assigned_agent_id` 过滤
5. **审计**：`audit_log` 加 4 字段，所有写动作（接管/回复/建单/工具调用）统一记
6. **验证**：e2e 加"租户 A 的坐席查不到租户 B 的会话"、"接管记 taken_by"、"审计能查出谁建的工单"

**验收标准**（可直接写进合同）
- [ ] 租户 A 任何接口都无法读到租户 B 的数据（含工具面板、导出、AI 助手）
- [ ] 每条 audit_log 能回答：谁、哪个租户、什么动作、什么对象
- [ ] 伪造 `customer_id` 或 `tenant_id` 请求体不影响实际查询范围

### 阶段二：运营与合规（P1，约 3-4 天）

1. **配额与限流**：租户级月会话数 / 并发坐席 / 每分钟请求数（对应风险审计 R7）
2. **看板**：租户级指标聚合（会话量/转人工率/首响/解决率/未命中 Top5）
3. **导出**：审计与会话按租户导出（异步任务）
4. **留存**：热 90 天 + 冷归档；删除工单（级联删 + 删除审计）
5. **抽样审计队列**：低置信/转人工/工单写入三类必抽（对应风险审计 R8）

### 阶段三：商业化（P2，约 3-4 天）

1. **套餐**：基础/专业/旗舰（会话数、坐席数、功能开关）
2. **计量与计费**：按席位 + 超额用量
3. **SLA 与告警**：可用性、首响、错误率阈值告警（对应风险审计 R9）
4. **多租户知识库**：政策/商品数据按租户定制（现在 mock.db 全共享）

## 五、toB 化的技术风险（提前识别）

| 风险 | 说明 | 对策 |
| :--- | :--- | :--- |
| **租户过滤漏掉一处 = 数据泄露** | 手工加 `WHERE tenant_id` 必然有遗漏 | ① 统一 Repository 层强制注入 ② e2e 交叉租户用例 ③ CI 加 SQL 静态扫描（禁止无 tenant 条件的查询） |
| 共享 sqlite 无法承受多租户 | 单文件锁，并发写会锁表 | 阶段一就换 Postgres（代码已支持 `PostgresTaskStore`） |
| WS 扇出注册表是进程内 | 多实例部署跨进程收不到 | Redis pub/sub（已留注释） |
| 现有 Mock 数据全共享 | 商品/政策按租户定制时冲突 | 加 tenant_id 联合主键，seed 按租户生成 |
| 审计只追加会无限增长 | 存储成本 | 分区表（按月）+ 冷归档 |
| 坐席 AI 助手会话共享 | `ASSIST_CONTEXT` 固定为 `"agent-assist"` | 改 `agent-assist:{tenant_id}:{agent_id}` |
| 权限在前端隐藏不算数 | 按钮藏了但 API 能调 | 全部校验在服务端；前端只做体验 |

## 六、toB 化的「不做什么」（避免过度设计）

| 不做 | 为什么 |
| :--- | :--- |
| 每租户独立部署（物理隔离） | 成本高；逻辑隔离 + 行级过滤足够中大型商家；超大型客户再走专有部署 |
| 自研 SSO | 接企业微信/钉钉/OIDC 即可 |
| 自研计费系统 | 接 Stripe/支付宝订阅，或先手工对账 |
| 租户自定义 Agent 拓扑 | 当前 6 域够用；开放自定义会让路由确定性失控（P3 再看） |
| 每租户独立模型 | 用同一模型 + 租户级 prompt 配置即可；成本才可控 |

## 七、toB 方案的对外讲解要点

**核心结论**：当前系统是单租户的 toC 客服 Demo，toB 化要补的不是功能，是**隔离、归属、追责**三件事——这也是 SaaS 采购方最先问的三个问题。

**三层展开**：
1. **隔离**：`tenant_id` 从 token 取不从请求体取；所有 SQL 强制过滤；跨租户返回 404 不返回 403（不泄露存在性）
2. **归属**：每条数据能回答"哪个租户、哪个人"——现在是空白（审计表连 actor_id 都没有）
3. **追责**：审计四要素（tenant/actor/action/target）+ 只追加 + 按租户导出

**优先级判断**：优先级上，**先做隔离和归属**（2-3 天，P0），因为这两项缺了根本不能卖；配额计费可以后补。而且我发现现有代码里 `tenant` 零命中，说明 PRD 要求了但实现落下了，这种'设计-实现差距'正是审查自己项目的价值。
