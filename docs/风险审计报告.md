## 二、完整校验链路对照（手册第三部分 3.1）

手册的端到端链路 vs 项目实际链路：

```
手册：用户输入 → 感知 → 状态 → 决策 → [AI 输出] → 前置约束 → 风险分层
        → 沙箱 → 执行前确认 → 生产执行 → 执行后验证 → 抽样审计 → 反馈闭环

项目：用户输入 → intake(规范化+风险词) → understand(LLM) → route(查表)
        → advance(Send) → domain_call → 域 ReAct → 工具执行(写库!)
        → Artifact → synthesize → deliver(仅校验 authority 字段)
```

**缺口标注**：
- ❌ **前置约束**：仅在商品域工具层有 scope（售后/政策无）
- ❌ **风险分层**：整条链路没有
- ❌ **沙箱**：没有
- ❌ **执行前确认**：没有
- ⚠️ **执行后验证**：`deliver` 只检查 `authority_domain` 是否存在（`graph.py:442-451`），**检查到了只打 warning，不阻断**——这是"看起来有校验其实没有"
- ❌ **抽样审计**：没有
- ⚠️ **反馈闭环**：只有留痕，没有回流

**链路级判定**：项目实现了"**可观测**"（trace/decision/audit），但**缺"可控制 + 可回滚"**——这正好对应 R2–R5 四个高危项。

## 四、风险清单与修法（按严重度排序）

> 每项给：现状证据（file:line）→ 攻击/故障场景 → 手册对照点 → 修法（按工作量分级）

---

### 🔴 R1｜售后域、政策域**完全没有权限校验**

**证据**
- `domains/merchandising/tools.py:29` 有 `ensure_scope`，4 个工具全部调用（`:50/62/81/107`）
- `domains/aftersale/tools.py` — `grep -c ensure_scope` = **0**
- `domains/policy/tools.py` — `grep -c ensure_scope` = **0**
- 更严重：`ensure_scope` 本身**默认放行**——`if got is None: return True`（`merchandising/tools.py:34-35`）

**场景**
1. 任何调用方（包括坐席工具面板、外部误配的客户端）不带 `scope` 就能调售后/政策全部工具；
2. 即使带了 scope，商品域的"未带=信任"语义意味着**漏传 scope 等于拿到全权限**；
3. 写操作 `create_ticket` 无权限保护 → 任意会话可建单。

**手册对照**：2.1 前置约束-权限约束（"AI 只能调用查询 API，不能调用删除 API"）+ 场景八

**修法**
- **P0（30 分钟）**：把 `ensure_scope` 提到 `shared/auth.py`，售后/政策所有工具补上；**默认拒绝**（`if got is None: return False`，dev 用 `INTERNAL_TOKEN` 显式注入 scope）
- **P1（半天）**：写操作单独 scope（`aftersale.write`），读用 `aftersale.read`——与 PRD 8.2 的"scope 精确到 skill"对齐
- **P2**：接 OAuth Client Credentials，scope 来自 token claim 而非 metadata 自称

### 🔴 R2｜没有风险分层（写操作与查询走同一条路）

**证据**
- `orchestrator/graph.py:279` `advance` → `:309` `domain_call` —— 不区分域的读/写属性
- `route_table.py:11` 的 `ROUTE_TABLE` 只有 `mode`（single/parallel），**没有 risk 字段**
- 全库无 `risk_tier` / `is_write` 之类的判据

**场景**
客户一句话 → LLM 选到 `ticket.create` → 直接写库。同一句话若选到 `product_lookup` → 只读。**两者经过完全相同的校验路径**。

**手册对照**：第一部分 1.3 工程落地（风险分类器）+ 第三部分 3.2 组合矩阵（高风险必须沙箱+确认+审计）

**修法**
- **P0（1 小时）**：给工具加元数据声明风险级别（装饰器 `@risk("high")` 或 `TOOL_TO_SKILL` 旁加 `WRITE_SKILLS` 集合），`domain_call` 委托时把风险级别带进 Artifact
- **P1（半天）**：`ROUTE_TABLE` 加 `risk` 字段；`synthesize` 前按风险级别走不同分支（高风险→确认流程）
- **P2**：动态定级（金额/客户等级/上下文），接到 M3 财务域时必须有

### 🔴 R3｜写操作**没有执行前确认**

**证据**
- `domains/aftersale/tools.py:85-100` `create_ticket`：函数体内直接 `INSERT`，无任何确认环节
- 编排链路 `domain_call`（`graph.py:309`）委托后直接消费结果，无"待确认"状态
- 全库无 `confirm` / `approval` / `pending_action` 机制（除转人工的 `pending_task_id`，那是澄清不是确认）

**场景**
1. 客户说"帮我建个工单"，AI 直接建了——客户其实只是想**问**怎么建；
2. LLM 参数抽取错误（sku 抽错、fault_type 抽错）→ 错误工单直接入库；
3. 客户重复说同样的话 → 多次建单（与 R5 叠加）。

**手册对照**：2.4 执行前确认（AI 自确认/系统硬确认/人工审批）+ 场景一"≤100 自动/100-500 自确认/>500 人工"

**修法**
- **P0（2 小时，收益最大）**：写操作改成**两阶段**——工具返回 `{"status":"pending_confirm","preview":{...},"confirm_token":"..."}`，编排层用 `interrupt()` 把 preview 发给客户确认（**复用现有 interrupt 机制，零新组件**），确认后再调 `ticket.create(confirm_token=...)` 真正落库
- **P1**：阈值分级（如工单金额/数量超阈值 → 转人工审批）
- **P2**：坐席侧写操作加二次确认弹窗（前端已有 `insert-btn` 模式可复用）

### 🔴 R5｜写操作**没有幂等**，工单号生成有竞态

**证据**
```python
# domains/aftersale/tools.py:88-92
row = conn.execute("SELECT COUNT(*) AS n FROM tickets").fetchone()
ticket_no = f"TK-{3001 + int(row['n']) + 1}"
conn.execute("INSERT INTO tickets(...) VALUES (...)", (...))
```
- **read-modify-write 竞态**：两个并发请求拿到同一个 `n` → 同号；
- **无唯一约束**：`tickets` 表的 `ticket_no` 是 PRIMARY KEY（`seed_mock.py` 建表），并发时第二个会报 `UNIQUE constraint failed` 而不是优雅去重；
- **无幂等键**：同一 `contextId + sku + fault_type` 重复调用会建多个单（PRD 7.7 设计了 `biz_key = contextId + action + target_id`，**代码里没有**）。

**场景**
1. 网络抖动 → A2A 客户端重试 → 建两个单；
2. 用户在澄清后重复确认 → 建两个单；
3. 两个坐席同时操作 → 一个报错（体验差）。

**手册对照**：2.5 执行后验证-幂等性（"重复执行是否产生副作用"）——**这是手册明确点名的必检项**

**修法**
- **P0（1 小时）**：`tickets` 加 `biz_key` 唯一索引（`contextId:sku:fault_type`），INSERT 用 `INSERT OR IGNORE` + `SELECT` 回读——**天然幂等**
- **P1**：工单号改用 UUID 或数据库序列（放弃 `COUNT+1`）
- **P2**：接 Saga 时把 `biz_key` 复用为补偿的幂等键

## 七、值得强调的审计结论

如果被问"你怎么做 AI 风控"，这套审计本身就是最好的答案：

1. **"我按三层风险模型给项目里每个 AI 动作定了级"**——A1 低风险/A3 中风险/A4 高风险，**分级之后缺口一目了然**。
2. **"我发现自己的写操作没有执行前确认"**——这不是"没想到做"，是"用手册标准审出来"。
3. **"最有价值的不是加沙箱，而是加幂等"**——沙箱是重的（要造快照），幂等是一个唯一索引的事，**投入产出比高 100 倍**。
4. **"我的低风险链路其实达标了，甚至优于手册**——有置信度路由 + 澄清 + 结构化输出，这三样对应的正是手册 2.1/3.3"。
5. **"缺的不是框架，是优先级"**——M3 财务域一接，金额类高风险动作就会出现，那时 R2/R3 必须已经在位。
